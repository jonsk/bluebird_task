# BlueBird 重构 · 后端模块详细设计

> 上级文档：`01蓝鸟重构方案.md`；同级前端文档：`03前端模块详细设计.md`。
> 本文档覆盖后端各业务模块（common/config、identity、org、task、file、audit）详细设计，统一遵循：
> - 接口前缀 `/api/v1`；统一响应体 `ApiResult{code,message,data,traceId}`，`code==0` 为成功。
> - 分层：`controller → application → domain → infrastructure`。
> - 逻辑删除 `deleted INTEGER`（**仅主实体表**，见 §1.6）；主键 snowflake `INTEGER`；审计字段由 `MetaHandler` 自动填充。
> - 模块依赖：`task → identity, org, file`；`audit ← 所有`；`common/config` 被所有依赖。
> - 仓库结构：本模块代码位于 Monorepo **`bluebird-task/backend/`**（总结构见 `01 §6`）；下文出现的 `src/main/...`、`db/migration/`、`mapper/` 等路径均相对 `backend/`。

## 1.3 统一响应体
```java
public record ApiResult<T>(int code, String message, T data, String traceId) {
    public static <T> ApiResult<T> ok()            { return ok(null); }
    public static <T> ApiResult<T> ok(T data)      { return new ApiResult<>(0, "ok", data, TraceContext.get()); }
    public static <T> ApiResult<T> fail(ErrorCode e){ return new ApiResult<>(e.code(), e.msg(), null, TraceContext.get()); }
}
```
- `traceId`：每次请求生成，贯穿日志（MDC）；响应头 `X-Trace-Id`。
- 约定：HTTP 状态码统一 200，业务状态用 `code` 表达。
- **缓存约定（修订 0309）**：所有返回用户/个人数据的 API JSON 响应统一写 `Cache-Control: no-store`（防代理/浏览器缓存私有数据）；静态资源 `/assets/**` 长缓存、`/index.html` `no-cache` 由 `WebConfig` 处理（`01 §11.4`）；文件下载/预览 `GET /files/{id}[/preview]` 按需 `Cache-Control: private, max-age=...`（不共享缓存）。
- **参数约定（修订 0309）**：**秘密一律不入 URL/query**——`token` 走 `Authorization` 头，密码/密钥走请求体；query 仅承载非敏感过滤/分页参数。所有 `GET` 查询参数视为可入访问日志（`code` 等一次性授权码属协议例外，见 §2.3）。

## 1.5 全局异常处理
```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public ApiResult<Void> biz(BusinessException e) { return ApiResult.fail(e.getCode()); }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ApiResult<Void> valid(MethodArgumentNotValidException e) { return ApiResult.fail(ErrorCode.PARAM_ERROR); }
    @ExceptionHandler(AccessDeniedException.class)
    public ApiResult<Void> denied(...) { return ApiResult.fail(ErrorCode.FORBIDDEN); }
    @ExceptionHandler(NoHandlerFoundException.class)   // API 404 统一转 NOT_FOUND（修订 RF6）
    public ApiResult<Void> notFound(NoHandlerFoundException e) { return ApiResult.fail(ErrorCode.NOT_FOUND); }
    @ExceptionHandler(Throwable.class)
    public ApiResult<Void> unhandled(Throwable e) { log.error("Unhandled error", e); return ApiResult.fail(ErrorCode.SYSTEM_ERROR); }
}
```
- 生产不向客户端暴露堆栈与内部细节，`traceId` 关联日志。

## 1.6 数据规范
### 逻辑删除
- **逻辑删除**（`deleted INTEGER not null default 0` + MyBatis-Plus `@TableLogic` 自动过滤）**仅用于主实体表**：`sys_user`、`task`、`category`、`sys_department`。
- **物理删除**（**无 `deleted` 列**）用于以下表：
  - 关系/关联表：`task_participant`、`tag`、`task_tag`、`task_collect`、`task_menu`、`task_menu_item`、`sys_user_department`；
  - 从属数据：`attachment`；
  - 审计日志：`audit_operate_log`/`audit_login_log`（物理追加，见 §6.2）。
- 说明（修订 F5/十三审）：原「业务表统一 `deleted`」表述与各模块 DDL 不符（上述关系/从属/日志表均无该列）。现统一为「**主实体表逻辑删除、关系/从属/日志表物理删除**」，实现者勿一律加 `deleted` 列。
- **硬约束（修订 R3，阻断修复）**：`mybatis-plus.global-config.db-config.logic-delete-field: deleted` 是**全局**的，MyBatis-Plus 会**对任何声明了 `deleted` 字段的 DO 自动注入 `WHERE deleted=0` / `UPDATE ... deleted=1`**。因此**明令**：
  1. 关系/关联表 `task_participant / tag / task_tag / task_collect / task_menu / task_menu_item / sys_user_department`、从属表 `attachment`、审计日志表 `audit_operate_log / audit_login_log` 的 **DO 一律禁止声明 `deleted` 字段**（类中不带 `private Integer deleted`，更不得加 `@TableLogic`）；
  2. 上述表的 **Mapper 一律物理删除**（`deleteById/delete(...)` 走真实 DELETE，不拼 `deleted=1`）；
  3. 仅 `sys_user / task / category / sys_department` 四个主实体 DO 允许声明 `deleted` 并加 `@TableLogic`。
  > 若任一从属/日志 DO 被误加 `deleted` 字段，MP 会对无该列的表拼 `WHERE deleted=0` → **SQL 列不存在报错**（启动即炸）。
- **启动期防误加断言（修订 R3）**：新增 `LogicDeleteGuard`（`ApplicationRunner` + `@Profile("!test")` 单测另覆盖）——在启动时反射扫描 `com.bbtc.bluebird` 下所有带 `@TableName` 的 DO，凡 `@TableName` 落在上述从属/日志表清单内的，**断言其字段集中不含 `deleted`**，  含则 `throw` 阻断启动（fail-fast）。单测 `LogicDeleteGuardTest` 逐表校验无 `deleted` 列，防后人误加（见 §1.12 测试与验收）。

### 1.7.1 静态资源与 SPA 回退（ADR-009 单制品）
- 前端 `dist` 在打包期注入 `src/main/resources/static/`，由内嵌 Tomcat 提供；**部署不使用 Nginx**，单 jar 对外。
- 放行静态资源：`/`、`/index.html`、`/favicon.ico`、`/assets/**`（**不含 `/api/v1/**`**）。
- **SPA 页面也必须在 Security 放行（修订 R29，阻断修复）**：浏览器**直接访问或刷新**深链（`/index`、`/allTask`、`/admin/org`…）是**文档导航**，不会带 `Authorization` 头。若这些页面路径不在白名单，用户拿到的是 `10002 未登录` 的 **JSON**——刷新即白屏/裸 JSON。页面路径由 `SpaRoutes.PAGE_PATTERNS` 统一定义，`SecurityConfig` 放行与 SPA 回退**共用同一份清单**，避免「加了页面忘了放行」。数据仍全部来自受保护的 `/api/v1/**`。
- **资源映射（修订 R1，阻断修复）**：`spring.web.resources.add-mappings: false` **仅**关闭 Spring Boot 对 `classpath:/META-INF/resources/`、`classpath:/resources/`、`classpath:/static/`、`classpath:/public/` 的**默认**静态映射（用于让未映射 API 走 `NoHandlerFoundException`）；它**不会**禁用 `WebMvcConfigurer.addResourceHandlers` 显式注册的处理器。因此必须在 `WebConfig` 中**显式注册** `ResourceHandlerRegistry`，否则 `/assets/*.js|css`、`/favicon.ico` 因 Accept 不含 `text/html`（不满足 SPA 回退条件）又无资源处理器 → **404 白屏**：
  ```java
  @Override
  public void addResourceHandlers(ResourceHandlerRegistry registry) {
      // 命中先于 SPA 回退；文件路径来自 classpath:/static/（打包期注入的 dist）
      registry.addResourceHandler("/assets/**")   .addResourceLocations("classpath:/static/assets/").setCacheControl(CacheControl.maxAge(365, TimeUnit.DAYS).cachePublic());
      registry.addResourceHandler("/favicon.ico") .addResourceLocations("classpath:/static/favicon.ico");
      registry.addResourceHandler("/")            .addResourceLocations("classpath:/static/");
      registry.addResourceHandler("/index.html")  .addResourceLocations("classpath:/static/index.html").setCacheControl(CacheControl.noCache());
  }
  ```
  - 长缓存仅对 `/assets/**`（Vite 文件名含 content hash，`immutable`）；`/index.html` 必须 `no-cache`（否则发版后旧 index 引用已清理的旧 hash 资源 → 404）。
  - SPA 回退只兜底**其余**页面路由；**已显式注册的资源轮不到它、也不会被误转发**。`DispatcherServlet` 先查 `@RequestMapping`→再查 `ResourceHttpRequestHandler`（此处注册）→无 handler 才 `throwExceptionIfNoHandlerFound` 抛 404。`/assets/**`、`/favicon.ico`、`/`、`/index.html` **优先由资源处理器服务**，不会落入 SPA 回退与 API 404。
- **SPA 回退实现（修订 R29）**：在 `WebConfig.addViewControllers` 中按 `SpaRoutes.PAGE_PATTERNS` 逐个 `addViewController(p).setViewName("forward:/index.html")`。**不用 `@RequestMapping` 注解**：注解元素要求编译期常量，无法引用 `SpaRoutes` 数组，会导致页面清单分裂成两份（原先的桩实现正是硬编码了少数路径，`/index`、`/allTask`、`/calendar/*` 等全部漏掉）。**API 的 404 仍返回 JSON `ApiResult`**，不被回退吞掉（未映射的 `/api/v1/**` 不在页面清单内）。
- **API 404 规范（修订 RF6）**：未映射的 `/api/v1/**` 由 Spring MVC `NoHandlerFoundException` 抛出并转 JSON `ApiResult{code:10004 NOT_FOUND}`——需 `spring.mvc.throw-exception-if-no-handler-found: true` + `spring.web.resources.add-mappings: false`（关闭默认映射、避免吞 API 404），并在 `GlobalExceptionHandler` 增加 `@ExceptionHandler(NoHandlerFoundException.class) → NOT_FOUND`；禁止交给 Spring 默认 HTML 404（前端 `http.ts` 统一按 `ApiResult` 解包，否则字段缺失抛错）。
- 缓存：`/assets/**` 长缓存 `immutable`（Vite 文件名含 content hash）；`/index.html` `no-cache`（见上，防发版旧 hash 404）。压缩用内嵌 Tomcat `server.compression.enabled=true`（替代 Nginx gzip）。
- **CI 校验（修订 R1/G6 叠加）**：`jar tf bluebird-task.jar` 断言同时存在 `static/index.html` 与至少一个 `static/assets/` 条目，防止前端产物未注入或 assets 缺失导致的白屏（见 `01 §11`）。
- 部署形态与构建接线见 `01 §11.0–§11.6` / `ADR-009`。

### 1.8.1 运行时配置释放（config extraction，ADR-010）
- 打包内置**默认配置** `classpath:/application.yml`（不含真实密钥，仅占位符 / 本地默认；§1.8 YAML 即为其基线）。
- 启动时由 `ConfigFileReleaser`（`ApplicationRunner`，位于 `config` 模块）检测运行目录（= jar 所在目录 / CWD）的 `application.yml`：不存在则把内置默认复制为 `./application.yml`；**已存在则不覆盖**（保留用户修改）。沿用旧系统 `BlueBirdApplication.checkAndCopyConfig()` 范式。
- 依赖置空后由 Spring 默认优先级 `file:./application.yml` 覆盖 `classpath:/application.yml`，用户改外部文件**重启即生效**。
- **密钥分类生成**（ADR-010）：
  - **首次自动生成并预填**：`jwt.secret`（随机 32B）、`BOOTSTRAP_ADMIN_PASSWORD`（强口令打印一次 + 强制首登改密）。自生成项**允许环境变量覆盖**（部署方显式指定则用之）。
  - **外部注入**（占位 `${...}`）：`SQLITE_URL`（可选）、`OIDC_CLIENT_ID/SECRET`、`WECHAT_CORP_SECRET`、`ORGSYNC_PUSH_TOKEN`——须与外部系统匹配。**无 DB/Redis 连接串**（SQLite 嵌入式，ADR-016）。
  - 生成的密钥仅写运行目录配置文件（`chmod 600`），不入仓库、不入内置默认。
  - **空值覆盖保护（J1）**：自生成密钥写入 `./application.yml`，**不在 `.env` 留空占位**——Spring 优先级「OS 环境变量 > `file:./application.yml`」，`.env` 经 `EnvironmentFile`/`env_file` 注入的**空串会覆盖自动生成值**，使首次 ADMIN 回落人工引导。`.env` 仅承载外部注入类；需自定义自生成密钥时填**非空**值（详见 `01 §15.1` / ADR-010 §5）。
- **目录配置**：日志目录 `logging.file.name`，文件存储目录 `app.storage.root`；首次释放即有可用默认值，用户可按需改。
- 详见 `01 §11.7`。

## 1.9 无缓存层与 SQLite 初始化（去 Redis，ADR-016）
**不引入任何缓存层**（无 Redis、无 Caffeine）——量级极小（≈100 人/日、≤2000 写/日），DB 直读足够（ADR-016）。

**SQLite PRAGMA 初始化**：`SqlitePragmaInitializer`（启动时逐条对连接执行）
- `PRAGMA journal_mode=WAL`（读写并发：读不阻塞写、写不阻塞读）
- `PRAGMA busy_timeout=5000`（写竞争等待 5s，避免 `SQLITE_BUSY`）
- `PRAGMA foreign_keys=ON`（开启外键约束，SQLite 默认关闭）
- `PRAGMA synchronous=NORMAL`（WAL 下兼顾性能与安全）

> 连接池 `maximum-pool-size=1`（SQLite 单写者）；**仅限单实例**访问同一 `.db` 文件（禁止多实例 / 网络文件系统）。

### 1.9.1 refresh 会话（落库，替代 Redis 白名单）
- 表 `sys_refresh_token`（见 §2.2）：签发的 refresh token 白名单**持久化落库**，登出/续签按行失效。
- **单活跃会话（修订 RF4）**：同一用户同时仅保留一个活跃 refresh（新登录覆盖旧行、旧 token 失效），符合「单人单机」私有化主场景；若未来需多端并存，改按 `jti` 保留多行（二期扩展）。

### 1.9.2 进程内临时状态（替代 Redis 的短命状态）
- **登录失败计数 / 锁定**：进程内 `ConcurrentHashMap`（key=username/IP，带过期清理），达阈值锁 `15min`（详见 §2.7）。重启即清零（单实例可接受）。
- **防重复提交**：`@RepeatSubmit` 切面用进程内 `ConcurrentHashMap`（key=`uri:userId`，短 TTL）。
- **org-sync 幂等锁**：进程内 `ReentrantLock`（单实例）。
- 上列均为**临时状态**（非缓存），不落库；进程重启丢失无业务影响。

## 1.10 通用组件
- `IdGenerator`：snowflake（**单实例**固定 `workerId=0`；SQLite 单写者、不支持多实例/集群，ADR-016）。
- **snowflake 时钟回拨兜底（修订 R7）**：同一实例内若系统时钟出现回拨（NTP 校时/时钟漂移），后生成的毫秒时间戳可能小于已用过的，导致重复 ID。兜底策略（择一实现并测试）：
  - **乐观等待**：检测到本次时间戳 `≤ 上次已用` 时，`自旋/睡眠` 等待至时钟追平（回拨量小、短时可追回时采用，默认）；
  - **拒绝降级**：等待超时（如回拨 > `LAST_MS_WAIT_MS`，默认 5s）仍未追平 → 抛 `IllegalStateException`（fail-fast，避免静默产生重复 ID）。
  - 单一实例默认 `workerId=0` 且依赖 OS 时钟；**启用容器/虚拟机更应保证时钟源一致**。
  - **单实例部署**（本方案目标）：`workerId=0` 固定即可；**多实例水平扩展不支持**（SQLite 单写者，ADR-016）。
- `IpUtils`：取 IP（含 X-Forwarded-For）。
- `JsonUtils`：Jackson + TEXT(JSON) 类型处理器（`cycle_rule` 等以 TEXT 存 JSON 字符串）。
- `DateUtils`：时区/格式化/日周计算。
- `FileExtUtils`：扩展名白名单、大小换算。
- `@RepeatSubmit` 注解 + 切面：**进程内 `ConcurrentHashMap`**（短 TTL）防重复提交（去 Redis，ADR-016）。

## 1.13 响应缓存与参数安全（实现约定，0309）

> 落实 `01 §12#12/#13`。两条约定以**过滤器/拦截器**实现，统一生效、无需各 Controller 处理。

### 1.13.1 `ResponseCacheControlFilter`（禁止缓存用户数据）
```java
public class ResponseCacheControlFilter extends OncePerRequestFilter { /* 见规则 */ }
```
- 注册：`FilterRegistrationBean`，`order` 在 Spring Security 之后、`TraceIdFilter` 之前；匹配 `/api/v1/**`。
- 规则：
  - **默认**：对 `/api/v1/**` 的 JSON 响应（`Content-Type: application/json`）写 `Cache-Control: no-store`（附 `Pragma: no-cache`）。
  - **例外·文件**：`GET /api/v1/files/**`（下载/预览）→ `Cache-Control: private, max-age=<可配>`，**不得** `public`（防止共享代理缓存个人文件）。
  - **不干预**：静态资源（`/`、`/assets/**`、`/index.html`、`/favicon.ico`）由 `WebConfig` 处理（`01 §11.4`）；`/actuator/**` 不处理。
- 说明：与「统一 200」并存——缓存头是 HTTP 头，不改响应体。

### 1.13.2 `QuerySecretGuard`（秘密不入 URL）
- 实现：`HandlerInterceptor#preHandle`（或 `OncePerRequestFilter`），对所有请求生效。
- 规则：若 **query 参数名**命中黑名单（大小写不敏感）`token / access_token / refresh_token / authorization / password / pwd / secret / client_secret`，直接拒绝 → `10001 PARAM_ERROR`（`ApiResult`，HTTP 200）。
- **例外**：`code`（一次性授权码）仅在 `/api/v1/auth/**/callback` 放行（协议要求，见 §2.3）。
- 目的：杜绝 token/密钥经 query 进入访问日志、浏览器历史与 `Referer`；配合 §1.3 约定（认证走 `Authorization` 头）。

### 1.13.3 测试 / 验收
- 测试：JSON 响应含 `no-store`；`GET /files/{id}` 为 `private`；带 `?token=` 的 GET 返回 `10001`；`/auth/wechat/callback?code=` 放行；静态资源头不受影响。
- 验收：所有用户数据响应不可被代理/浏览器缓存；含敏感参数名的请求被拒；`X-Trace-Id`、静态资源缓存策略不受这两条约定影响。

## 2.3 认证流程
> 默认 `provider=LOCAL`：仅走下方「账号密码登录」，外部认证不装配（OIDC/WECHAT 为可选，见 2.1）。
### 账号密码登录
```
POST /api/v1/auth/login {username,password}
1. 参数校验  2. 锁定检查（失败计数达阈值 → `20006 ACCOUNT_LOCKED`，见 §2.7）  3. loadUserByUsername + BCrypt  4. 禁用/删除校验
5. 签发 access+refresh（refresh 写白名单表 `sys_refresh_token`）  6. 登录日志（成功/失败/锁定）  7. 返回 TokenVO+用户摘要
   （失败 → 计数 +1 并按阈值锁定；成功 → 计数清零）
```
### OIDC 外部认证（provider=OIDC，仅启用时；ADR-008，Spring Security OAuth2 Client，过滤器整页跳转）
```
前端: GET /api/v1/auth/external/config → {provider:"OIDC"}（前端仅据此决定是否渲染外部登录按钮，不自管授权地址）
      点击「OIDC 登录」→ 前端整页跳转【Spring 授权发起端点】/oauth2/authorization/oidc（修订 R9）
发起: Spring Security OAuth2 Login 过滤器生成并管理 state/nonce（服务端持有，防 CSRF/重放），302 → OIDC IDP 登录页（Google/Keycloak/Casdoor/竹云等）
跳转: IDP 认证后 302 重定向回回调地址（浏览器整页，非 XHR）
回调: GET /api/v1/auth/external/callback（OAuth2LoginAuthenticationFilter 拦截，state 校验，code→id_token）
1. Spring Security 交换 code→id_token → 解析 sub（= externalId）+ name/email
2. 查 sys_user(external_id=sub, deleted=0)
   - 有：校验 status → 签发 token
   - 无且 auto-create-user=true：自动建号（role_code=COMMON, dept_id=NULL）→ 签发 token
   - 无且 auto-create-user=false：拒绝（NO_PERMISSION_EXTERNAL）
3. 写登录日志
4. successHandler 302 重定向到前端 https://<app>/oauth/success#access_token=..&refresh_token=..（失败带 error；hash fragment 传 token，前端读后 replaceState 清除，修订 RF2）
```
### 企业微信认证（provider=WECHAT，仅启用时；ADR-008 例外，独立 Controller 回调）
```
前端: GET /api/v1/auth/external/config  → {provider:"WECHAT", corpId, agentId}
      前端渲染企微扫码组件 → 扫码后获得授权 code（前端 XHR 直调后端，企微无需服务端会话状态）
回调: GET /api/v1/auth/wechat/callback?code=xxx（独立路径，Controller + WechatIdentityAdapter）
1. WechatIdentityAdapter.loginByCode(code) → userid（= externalId）
2. 查 sys_user(external_id=userid, deleted=0)，无 → NO_PERMISSION_EXTERNAL（企微不自动建号）
3. 校验 status  4. 签发 token，返回 TokenVO 给前端
```
> OIDC 用户可自动建号（首次登录即创建，dept_id=NULL）；企微用户不自动建号（须先由组织同步或 ADMIN 手建）。
> 修订 M1（独立审核收敛，取代原 F6）：**OIDC 与企微回调地址拆分**——OIDC=`/api/v1/auth/external/callback`（Spring Security OAuth2 过滤器，整页 302 跳转，非 XHR）；企微=`/api/v1/auth/wechat/callback`（独立 `Controller` + `WechatIdentityAdapter`，前端 XHR 直调）。二者不再共用 URL。OIDC 需显式 `oauth2Login().redirectionEndpoint().baseUri("/api/v1/auth/external/callback")` 重绑定过滤器仲裁（仅改 `registration.oidc.redirect-uri` 不生效）；成功经 `AuthenticationSuccessHandler` 签发 app token 后 **302 到 SPA `/oauth/success#access_token=..&refresh_token=..`**（hash fragment 传 token 防落入历史/Referer/日志，前端读后 `replaceState('#')` 清除，修订 RF2），前端 `OidcSuccessView` 收 token（与 01 §7.6 一致）。
### Token
- access 短效（Bearer）；refresh 长效，`POST /api/v1/auth/refresh` 校验白名单表 `sys_refresh_token` 续签；登出删除该行（去 Redis，ADR-016）。

## 2.4 权限
- **角色集合（修订 0306/Q1）**：`role_code` 取值扩为 `ADMIN` / `AUDITOR`（审计员，**只读**审计日志）/ `USER_MANAGER`（用户与组织管理）/ `COMMON`（默认）。**仍不建 `sys_role` 表**（ADR-003 成立），角色以单值枚举承载。
- 任务相关默认登录即可；管理操作用 `@PreAuthorize`：建/禁用户、组织同步 = `hasAnyRole('ADMIN','USER_MANAGER')`；审计日志查询 = `hasAnyRole('ADMIN','AUDITOR')`；其余 ADMIN 专属。
- **职责分离（SoD，0306/Q1）**：`AUDITOR` **仅可读审计日志**，无业务写权限；生产可分配独立审计账号，避免「操作者 = 审计者」。
> 修订 R6：`hasRole('ADMIN')` 由 `LoginUser.roleCode` → Spring Security `ROLE_ADMIN` Authority 转换（在 `MyUserDetailsService` 装配 `LoginUser.authorities` 时映射），**无需角色表**；`role_code=COMMON` 即普通用户。勿据此重建 `sys_role` 等表（见 ADR-003）。
> 修订 0306/Q1：角色由单 `ADMIN/COMMON` 扩为**四值枚举**（新增 `AUDITOR`/`USER_MANAGER`）；`ADMIN` 仍含全部权限（含审计），受限角色供职责分离。`LoginUser.authorities` 增 `ROLE_AUDITOR`/`ROLE_USER_MANAGER` 映射。
> 修订 R11：**断言测试**——`MyUserDetailsServiceTest` 校验 admin 用户 `authorities` 含 `ROLE_ADMIN`、common 用户不含，确保 `role_code→ROLE_ADMIN` 映射装配正确，防 `hasRole('ADMIN')` 因映射缺失导致管理接口全 403（见 §2.7 测试）。

## 2.7 安全 / 测试 / 验收
- BCrypt，不回传明文；OIDC client-secret / 企微 corp-secret 仅后端持有，`/external/config` 不返回 secret；登录失败统一 `BAD_CREDENTIALS`。
- **登录防暴破（0306/Q5，本期）**：同用户名/IP 维度失败计数（**进程内 `ConcurrentHashMap`，窗口+TTL 清理**，去 Redis，ADR-016）；达阈值（默认 5 次）锁定 `15min`，锁定期间返回 `20006 ACCOUNT_LOCKED`；成功登录清零。阈值/TTL 外部化配置（`app.security.login-max-fail` / `login-lock-seconds`）。CAPTCHA/MFA 列二期。
- **安全响应头（0306/Q5，本期）**：`SecurityConfig` 统一注入 `Strict-Transport-Security` / `Content-Security-Policy` / `X-Frame-Options: DENY` / `X-Content-Type-Options: nosniff` / `Referrer-Policy`（无 Nginx，须应用层兜底）；配合网关强制 HTTPS。
- **密码策略 / 附件病毒扫描 / 存储加密 / HTTPS-only 强制**：**列二期**（见 `01 §3`）。
- 测试：登录成功/失败/禁用/**锁定与解锁（失败计数）**、OIDC 回调（Mock id_token）、企微 code 解析（Mock WechatIdentityAdapter）、OIDC 首次登录自动建号、token 签发/刷新/登出、权限注解、改密失效。
- 验收：默认 `provider=LOCAL` 下**仅账号密码登录闭环**；启用 OIDC/企微后对应登录闭环（OIDC + 账号密码 / 企微 + 账号密码）；`provider=LOCAL` 时 `external/config` 返回 `LOCAL` 且不装配外部源；无权限用户被拒；OIDC 首次登录自动建号正确；普通用户不能调 ADMIN 接口；**连续登录失败触发锁定**；**响应含安全头**；登录日志记录；config 不泄密。

## 3.3 组织同步设计（四模式，ADR-008，由 `app.orgsync.mode` 配置）

### 模式 1：SCIM（被动接收标准推送）
```
IDP（Keycloak/Casdoor/Okta/Entra ID）──推送──> POST /api/v1/scim/v2/Users
                                              POST /api/v1/scim/v2/Groups
ScimController 接收 → upsert sys_user / sys_department / sys_user_department
Bearer token 鉴权（ORGSYNC_PUSH_TOKEN）
```
- 零代码：任何 SCIM 2.0 兼容 IDP 都能推送，无需写 Adapter。
- 幂等：以 SCIM `id` 为 `external_id` / `corp_id` 映射，upsert。
- **Group 映射口径（修订 L4）**：SCIM `Group` 的语义（权限组）与「组织部门」不同——本系统仅将 `Group` **按其名称映射为部门**（`sys_department`），**忽略其权限语义**（本系统权限由 `sys_user.role_code` 单一表达，ADR-003）；`Users 的 memberships` 落到 `sys_user_department`（部门归属，非权限）。

### 模式 2：PULL（定时主动拉取）
```
手动触发 或 每日 01:00 @Scheduled
1. JVM 本地锁（`ReentrantLock`，防并发；单实例，ADR-016）
2. OrgSyncService 调 OrgSyncAdapter.syncOrg()（企微/钉钉/飞书）
3. 按外部源部门 id upsert sys_department(corp_id)
4. 按外部源用户 id upsert sys_user(external_id)；已存在更新、不存在新增、移除标记失效
5. 维护 sys_user_department（多部门）
6. 记录 SyncResult，释放锁
```
- 幂等：以外部源部门/用户 id 为映射；同步**不删实体，仅标记失效保留历史归属**（修订 L5：外部源已移除的用户置 `sys_user.status=DISABLED`，与 §2.3 登录「禁用校验」衔接——DISABLED 用户登录被拒但不删行，其历史任务归属保留）。

### 模式 3：PUSH（被动接收私有推送）
```
IDM（竹云等）──推送──> POST /api/v1/org/push
OrgPushController 接收 → OrgPushAdapter.parse(payload) → upsert sys_user / sys_department / sys_user_department
Bearer token 鉴权（ORGSYNC_PUSH_TOKEN）
```
- 需写定制 `OrgPushAdapter` 解析私有 JSON 格式。

### 模式 4：NONE（不同步）
- 用户由 OIDC 首次登录自动建号（`dept_id=NULL`），ADMIN 手动分配部门。

## 4.2 数据模型（完整 DDL）
```sql
CREATE TABLE task (
    id          INTEGER PRIMARY KEY,
    parent_id   INTEGER,                                 -- 空=主任务，非空=子任务/步骤
    title       TEXT NOT NULL,
    content     TEXT,
    status      TEXT NOT NULL DEFAULT 'ACTIVE',          -- ACTIVE/DISABLED/ARCHIVED
    completed   INTEGER NOT NULL DEFAULT 0,              -- 0/1
    priority    TEXT NOT NULL DEFAULT 'MEDIUM',          -- LOW/MEDIUM/HIGH/URGENT
    due_at      TEXT,                                    -- 截止时间（周期任务=基准 dtstart，见 §4.3）
    remind_at   TEXT,                                    -- 提醒时间
    cycle_rule  TEXT,                                    -- 周期规则（TEXT 存 JSON），完整字段见 §4.3（计算式展开）

    category_id INTEGER,
    owner_id    INTEGER NOT NULL,                        -- 归属人

    updated_by  INTEGER

## 4.3 领域模型与状态机
```
status: ACTIVE / DISABLED / ARCHIVED；completed: 0/1（独立于 status，仅对非周期任务有阻塞语义）
非周期: ACTIVE --complete--> completed=1；--uncomplete--> completed=0
        complete() 仅 ACTIVE 且未完成可完成；重复完成 → TASK_ALREADY_COMPLETED
周期(recurring): complete(id, dueAt) / uncomplete(id, dueAt) 走【独立分支】(修订 R2)
        ——模板行 completed 【恒为 0，不参与完成位】；完成/取消仅推进/回退 cycle_last_completed
        ——故下一实例可连续完成，不会被 TASK_ALREADY_COMPLETED 拦截
```
- 子任务：`parent_id != null`；可带 due/remind/priority/completed；主任务完成不强制联动子任务。
- **周期规则 `cycle_rule`（TEXT 存 JSON，计算式展开）**：
  ```json
  {
    "freq": "DAILY|WEEKLY|MONTHLY",   // 频率
    "interval": 1,                    // 每 N 个 freq 发生一次（≥1）
    "dtstart": "2026-10-01T18:00:00+08:00", // 基准：首次发生（= task.due_at 初始值，时区由 tz 表达）
    "byDay": ["MO","WE"],             // 仅 freq=WEEKLY 时有意义（可选，缺省=每 7*interval 天）；DAILY/MONTHLY 忽略（修订 M2 边界）
    "count": null,                    // 可选：总发生次数（与 until 互斥，null+until=null 表示无限）
    "until": null,                    // 可选：最后发生日期（含），与 count 互斥
    "tz": "Asia/Shanghai"             // 时区（缺省 GMT+8），所有日期按此计算
  }
  ```
  > 边界（修订 M2）：`byDay` 仅对 `freq=WEEKLY` 生效（列举一周内周几，如 `["MO","WE","FR"]`），`freq=DAILY/MONTHLY` 时 `byDay` 忽略；`count` 与 `until` 互斥，二者皆空=无限循环。

**周期任务展开策略（计算式展开，修订 M2）**：
- **不物化多行**：一个周期任务在 `task` 表**只存一行模板**（`cycle_rule` + `due_at`=dtstart + `cycle_last_completed`）。
- **未来发生由查询计算**：六大视图/日历查询时，取某用户的周期任务，以 `due_at`（dtstart）为基准、按 `freq/interval/byDay` 递推，落在查询时间窗 `[start,end]`（如「今天」「今天+7」）内的实例即为可见项；**不会因单一 `due_at` 而漏掉未来多次**。
- **完成推进（修订 R2，阻断修复）**：完成某实例时，**绝不置模板行 `completed=1`**（该字段仅对非周期任务有阻塞意义；recurring 模板行 `completed` 恒为 `0`，不作完成位——否则次日重调 `complete` 会被状态机 `TASK_ALREADY_COMPLETED` 永久拦截后续所有实例）。完成仅**写 `cycle_last_completed = 该实例 due_at`**；`complete(id, dueAt)` 传当前待完成实例的 `due_at`，校验其为展开的「下一个未完成实例」后覆盖式推进。查询展开时跳过 `≤ cycle_last_completed` 的实例，从下一未完成实例展示，并触发下一条提醒。历史完成记录由 `audit_operate_log` 保留（不去物化行）。
- **取消周期**：清空 `cycle_rule`（置 NULL）即转普通任务，`due_at` 保留当前实例时刻。
- **recurring 完成/取消完成分支（修订 R2，阻断修复）**：
  - `complete(id, dueAt)` 仅 `status=ACTIVE` 时允许；校验 `dueAt` 为 `CycleExpander(rule, lastCompleted, start=dueAt, end=dueAt)` 命中的**下一个未完成实例**（即 `dueAt > lastCompleted` 且是该规则在 `dueAt` 处的一次合法发生）→ **仅写 `cycle_last_completed = dueAt`**，模板行 `completed` 不变（恒 0）。不满足（`dueAt ≤ lastCompleted` 或非合法发生实例）→ 抛 `TASK_ALREADY_COMPLETED`（对「已完成的旧实例重复点完成」仍保守报错，避免回退错乱）；`dueAt` 为空则取当前下一个实例。
  - `uncomplete(id, dueAt)` 校验 `dueAt` 为当前 `cycle_last_completed`（最近完成实例）→ **回退 `cycle_last_completed`** 到前一未完成边界（截止至恰好早于 `dueAt` 的上一发生时刻；若 `dueAt` 即首个实例则置 `NULL`）。回退后该实例重新成为待办，可再次 complete。非该最近实例 → 抛错。
  - 与状态机的解耦：因模板行 `completed` 恒 0，recurring 的 `complete/uncomplete` **不读、不写** `completed`，故不存在"重复完成被 `TASK_ALREADY_COMPLETED` 唯独针对 completed=1 拦截"的路径；recurring 的"已完成/取消"完全由 `cycle_last_completed` 表达。前端列表/日历对每个展开实例的"✓"操作即调 `{id}/complete` 并带上该实例 `dueAt`。
- 实现：`CycleRule` 值对象 + `CycleExpander`（纯函数：`(rule, lastCompleted, start, end) → List<Instant>`），含末次递增、周几映射、时区换算；纳入 §4.7 测试（周期解析/展开/边界，含 `count`/`until` 终止与 `byDay` 边界，及 R2 的连续完成/回退/重复完成报错）。

**与视图/计数过滤的衔接（修订 RF1）**——模板行 `completed`/`cycle_last_completed` 表达「已完成的最近一次实例」，**其当前待办状态由展开计算决定**，故查询层对 recurring 模板**不做 `completed=0` 硬过滤**（R30 起对非周期任务同样不过滤），避免未来实例被「未完成」过滤误杀：
- **列表/日历**：非 recurring（`cycle_rule IS NULL`）按 `R30` 口径（**不做 `completed` 过滤**，已完成排最后）；recurring（`cycle_rule IS NOT NULL`）不按 `completed` 过滤（模板行 completed 恒 0，见 R2），改为判断其**下一个未完成实例** `next = CycleExpander(rule, lastCompleted, start=now, end=now).first()` 是否落在查询窗口 `[start,end]`——在窗口内可见，否则不可见（含已无未来实例的终止模板）。
- **counts()**：recurring 按**展开实例数**计数（计算窗口内未完成实例数），不按模板行 `completed` 计。
- 伪代码（简化）：
  ```
  selectCycleTasks(user, window): 
     for t in tasks(user, cycle_rule IS NOT NULL):
        nexts = CycleExpander(t.rule, t.lastCompleted, window.start, window.end)
        if nexts.notEmpty(): emit(nexts)   # 每个 next 实例按视图归属/所有权判定
     for t in tasks(user, cycle_rule IS NULL):
        if t.completed == 0 and inWindow(t.due_at, window): emit(t)
  countCycle(user, scope):
     sum over recurring tasks of CycleExpander(rule, lastCompleted, scope.start, scope.end).size()
  ```

## 4.4 六大视图查询口径
| 视图 | 条件 |
|---|---|
| 我的一天 (day) | owner 或 participant(me) 且 **`created_at` 在所选日期当天**（＝当天**新建**的任务） |
| 未来7天 (week) | `due_at` ∈ [所选日期, 所选日期+7) |
| 我@Ta的 (joined) | participant_role=CC 且 user_id=me |
| 分配给我的 (assigned) | participant_role=ASSIGNEE 且 user_id=me |
| 我的收藏 (collect) | task_collect.user_id=me |
| 全部任务 (all) | owner=me 或我参与/被分配 |
- 默认 `deleted=0`；排序：逾期 > 临期 > 普通 > 已完成，同优先级按 due_at 升序。
- **已完成任务不过滤（修订 R30）**：六大视图**一律不过滤 `completed`**——已完成的任务仍留在列表里，
  由 `TaskSorter` 的 `rank=3` 排到**最后**，前端以删除线（`.bb-task-card__title.is-done`）呈现。
  旧系统同样是「未完成 + 已完成」都在，只是分两次查询（`completeStatus=0`/`1`）渲染成
  「未完成区 + 已完成折叠面板」（见 `docs/frontend-baseline/contracts/BbTaskList.md`）。
  曾因 `day`/`week` 加 `completed=0` 导致「一勾完成就消失」（用户反馈）；
  `/tasks/count` 复用同一 `collect`，故计数同样包含已完成（与旧 `/task/record/count` 口径一致）。
- **步骤/子任务隔离（修订 R27）**：六大视图、`/tasks/count` 与 `/tasks/calendar` **一律排除
  `parent_id IS NOT NULL` 的行**；步骤只出现在父任务详情的 `subtasks`（及 `GET /tasks/subtasks`）中。
  旧系统步骤存于独立子表（其 `parent_id` 注释为「父级ID（task_record表中的id）」），天然不会混进
  `task_record` 的列表查询；本重构步骤与父任务同表，**必须在列表查询里显式排除**，
  否则每加一个步骤，视图与计数中就多出一条「任务」（用户反馈 BUG）。
- **「我的一天」口径（修订 R26，对齐旧系统）**：旧系统 `TaskRecordServiceImpl.getDayTask` 的过滤是
  `task_setup_time LIKE 'yyyy-MM-dd'`，而旧库 `task_setup_time` 的列注释为**「任务建立时间」**
  （见旧 `sql/02_create_tables.sql`），即**当天新建的任务**，与截止时间无关；旧 `getWeekTask` 才按
  `DATE_ADD(task_setup_time, INTERVAL 7 DAY) > task_alarm_time` 走时间窗。
  旧前端「我的一天」页的日历把所选日期作为 `taskSetupTime` 传入，故该视图的 `date` 参数语义是
  **任务建立时间**，本重构保持一致：`day` 按 `created_at` 取当天（取默认值即「当天新建」），
  `week` 按 `due_at` 取 `[date, date+7)`。
  周期任务在 `day` 下**不展开实例**，按模板行 `created_at` 归属当天（与旧系统一致）。
- **status 过滤（修订 R4）**：六大视图**默认仅展示 `status='ACTIVE'`** 的活动任务；`DISABLED`（停用）与 `ARCHIVED`（归档）**默认不出现在六大视图**。归档查看经「全部任务」视图的 `status=ARCHIVED` 筛选（可选筛选参数，非独立视图）提供；停用不可恢复进活动（后续版本再放开）。

> 说明：`ARCHIVED` 是任务的生命周期终态（语义化归档，区别于 `deleted` 的待删软删位）；`DISABLED` 是临时停用（保留数据仅不进活动列表）。
- **recurring 豁免（修订 RF1/R30）**：视图层已**不再**对非周期任务做 `completed=0` 过滤（见上「已完成任务不过滤」），故非周期任务与周期任务在这一点上口径一致；周期任务仍按其**展开实例**判定可见性（模板行 `completed` 恒为 0，不参与过滤）。
- **关键字搜索（0305/D3）**：`GET /tasks?scope=...&keyword=`，`keyword` 对 `title`/`content` 做**大小写不敏感子串匹配**（`ILIKE '%kw%'`，`deleted=0`），与 `scope`、排序规则叠加；空 `keyword` 不筛选。本期**不含**多字段高级筛选/全文检索引擎。
- **组织级只读可见性 / 下属筛选（0305/D1，ADR-012）**：
  - **可见性（读）**：当前用户对任务 T 可见 ⟺ `T.owner=me` ∨ `me∈participants(T)` ∨ `ADMIN` ∨ `∃u∈{T.owner}∪participants(T): u∈subordinates(me)`（`subordinates(me)` = `me` 为负责人的部门**递归子树**内用户，排除本人）。
  - **列表筛选**：`GET /tasks?scope=all&subordinate=true` 返回「下属相关任务」（`T.owner∈subordinates(me)` 或存在参与人 ∈ `subordinates(me)`），**只读**；默认 `false`（不改变六大视图现状）。
  - **合规开关（0306/Q3）**：组织级可见性受 `app.security.manager-can-read-subordinate`（**默认 `false`，关闭**）控制；关闭时主管**不可**读下属任务。开启须在部署侧**明示告知**并在本项记录 PIPL 依据（见 `06合规对照表.md`）。
  - **敏感读审计（0306/Q3+A4）**：主管读取「非本人参与」的下属任务（详情/列表命中）记入 `audit_operate_log`（`action=read_subordinate`）。
  - **详情 / 子任务 / 日历**：按上述可见性放行（可见即只读）。
  - **写权限不受影响**：仍由 §4.7（`owner/assignee/cc/ADMIN`）决定；主管对下属任务**只读**。
  - **计数**：`/tasks/count` **不**计入下属任务（保持六大视图计数语义）。

## 4.7 事务 / 性能 / 权限
- 创建任务：task + participant + task_tag + category 同一事务。
- 删除（修订 RF7）：软删 task + 级联软删子任务 + 清理关联表；**关联的 `attachment` 行物理删除，并同步 `FileStorage.delete(relativePath)` 删磁盘物理文件**（`{root}/{yyyy}/{MM}/{snowflake}.ext`），避免孤儿文件/磁盘泄漏。软删恢复仅恢复任务记录、不复活附件（文档明确此语义）；附件磁盘删除失败记错并进入孤儿清扫（见 §5.6）。
- **删除不可逆语义（修订 R5）**：任务本身是 `deleted` 软删（可廉价恢复 task 行），但**删除时关联数据（participant/tag/collect/menu_item）与附件文件已物理清除**——因此**误删后无法原样恢复完整数据**，实际等于「清空后软删」：恢复仅回任务壳（标题/描述/due 等 `task` 属性），参与人/标签/收藏/附件均丢失。若需可恢复的完整快照保护，应使用**归档 `ARCHIVED`**（保留全部关联，不物理清理）而非删除。**删除语义定义为「不可逆」**：有恢复诉求请走归档；删除操作对 `ADMIN` 与任务参与者提示「将清空关联数据、不可恢复」（前端二次确认文案，见 03 §2.3）。
- 六大视图走索引；「全部任务」分页 + join；日历按区间 + 索引；**counts 直接按需计算**（去缓存，ADR-016）。
- **recurring 展开性能（修订 G5/ADR-016）**：`CycleExpander` 对每个周期任务的展开实例数受窗口限制（自然受 `[start,end]` 长度约束）；对单窗口超大区间（如「全部任务」年视图）做**展开上限保护**（每任务单窗口最多 N 实例，超出截断并提示）。**counts 不缓存**（量级极小，DB 直算足够），计数实时、无滞后。
- 权限（修订 0306/Q2）：**可写** = `owner` / `assignee` / `ADMIN`；**`CC`（我@Ta）改为「知会只读」**，不可写任务字段（修正旧 RF3 将 CC 视为可写）；写操作前 `TaskAuthService.assertWritable(taskId, userId)` 校验当前用户 ∈ {owner, assignee, ADMIN}。
- **乐观锁（0306/Q4）**：`task` 增 `version`（`@Version`），`PUT /tasks/{id}`、完成/取消完成等更新须携带 `version`；版本不匹配返回 `code=10006 VERSION_CONFLICT`（**HTTP 仍 200**，遵循 §1.3 全局约定；见 §4.5/§4.6），前端据此提示「内容已被他人修改，请刷新」。`category`/`menu` 等主实体同法。
- **分类共享范围（0306/P1，ADR-015；修订 0308）**：`category.scope ∈ {PERSONAL, DEPARTMENT, ORG}`（默认 `PERSONAL`）。
  - **读可见**：`PERSONAL` → `owner_id = 我`；`DEPARTMENT` → `dept_id ∈ 我所在部门`；`ORG` → 全部登录用户。`GET /categories` 返回三者合并树，`?scope=` 可选过滤。
  - **写**：`PERSONAL` → 创建者；`DEPARTMENT` → 创建者、该部门负责人（`sys_department.leader_user_id`）、ADMIN；`ORG` → `ADMIN`/`USER_MANAGER`。写前 `CategoryAuthService.assertWritable`。
  - **约束**：`DEPARTMENT` 必填 `dept_id`；`PERSONAL`/`ORG` 忽略 `dept_id`。`task.category_id` 可引用任意**可见**分类（建/改任务时校验 `assertVisible`）。
  - **无数据迁移**（全新部署）：如未来导入旧分类数据，一律置 `PERSONAL`（见 `01 §8.3`）。**部门子树共享/跨部门共享本期不做**（仅本部门 + 全员两级），避免复杂。
- **读可见性（0305/D1，ADR-012）**：读操作（详情/子任务/日历/列表）前 `TaskAuthService.assertVisible(taskId, userId)` 校验当前用户 ∈ {owner, assignee, cc, ADMIN} **或**「任务 owner/参与人 ∈ 我的下属集合」。**可见 ≠ 可写**：主管对下属任务为**只读**（写操作仍走 `assertWritable`）。`subordinates(me)` 由部门负责人关系（`sys_department.leader_user_id`）+ 部门树递归解析，结果**默认直算**（去缓存，ADR-016；如需可加进程内短时缓存）。

> 修订 0306/Q2 口径说明：**可写**仅 `owner` / `assignee` / `ADMIN`；`CC`（被 @ 的知会者）**只读**，不可编辑任务。前端 `BbTaskCard`/`BbTaskDetailDrawer`/`BbParticipantList` 与之对齐（CC 用户不显示写入口）。
- 测试：状态机、六大视图口径、子任务级联、收藏去重、CRUD、权限、周期解析与计算式展开（`CycleExpander` 递推/终止/时区边界，及 **R2**：recurring 连续完成不复用 `TASK_ALREADY_COMPLETED`、`uncomplete` 回退、重复完成旧实例报错）；**组织级可见性**（`assertVisible`：下属任务可见且只读、非下属拒绝、ADMIN 全量、`subordinate=true` 筛选口径）。
- 验收：六大视图口径与 §4.4 设计一致；完成/收藏联动；子任务闭环；排序正确。

- 测试：上传成功/超大/非法类型/空文件、目录穿越、下载删除、并发、孤儿清扫幂等。

## 6.3 操作日志（AOP）
```java
@Target(METHOD) @Retention(RUNTIME)
public @interface OperateLog { String module(); String action(); }
```
```java
@OperateLog(module="task", action="complete")
@PostMapping("/{id}/complete")
public ApiResult<Void> complete(@PathVariable Long id) { taskApp.complete(id); return ApiResult.ok(); }
```
切面：记录开始时间 → 执行方法 → status 成功/失败 → 组装（module/action/uri/参数脱敏/user_id/ip/ua/duration）→ **落库（关键事件同步、其余异步；见 §6.7）**。
- 参数脱敏（修订 0306/Q8）：密码/token 等黑名单字段替换 `***`；**可配置敏感字段**（如任务 `content`、备注）按 `app.audit.mask-fields` 掩码；查询类默认不记（**敏感读除外**，见 §4.4「敏感读审计」）。
- **可见性相关操作必记（0306/Q3）**：`leader_user_id` 变更（部门负责人）等直接影响可见性的高风险操作**强制标注 `@OperateLog`**，纳入审计。

## 6.4 登录日志
- identity 登录成功/失败/**锁定**处调用 `LoginLogService.record(username, success, ip, ua)`（不采集 IP 属地定位，精简依赖）。**登录成败与锁定为关键审计，须可靠落库**（见 §6.7）。

| GET | /api/v1/audit/operates | 操作日志分页 | `hasAnyRole('ADMIN','AUDITOR')` |
| GET | /api/v1/audit/logins | 登录日志分页 | `hasAnyRole('ADMIN','AUDITOR')` |

## 6.7 设计 / 安全 / 测试 / 验收
- **落库策略（修订 0306/Q8：本地缓冲双写）**：一般操作日志经**本地缓冲（追加文件/内存队列）→ 异步批量入库**，避免直接 `@Async` 在崩溃/队列未刷时丢失；**关键事件**（登录成败、账号锁定、任务删除、用户禁用、权限/角色变更、`leader_user_id` 变更、敏感读）**同步写库**（`app.audit.sync-actions` 配置，默认含上述项）。
- **保留期与防篡改（0306/Q3，本期定义策略、防篡改实现可二期）**：保留期默认 **≥180 天**（`app.audit.retention-days`，过期归档/清理任务）；审计表**只追加、不提供改/删接口**；防篡改（hash 链 / WORM / 独立只读存储）列为**二期增强**（本期在文档声明该差距）。
- 敏感字段脱敏（可配置）；查询鉴权 `hasAnyRole('ADMIN','AUDITOR')`（**审计员可读**，职责分离）。
- 测试：切面成功/异常、脱敏、缓冲+同步双路径、登录日志/锁定日志、分页过滤、`AUDITOR` 只读权限（不能写业务）。
- 验收：关键操作自动记日志（参数/IP/时长/结果）；登录成败与锁定均记录；敏感字段不落库；关键事件同步可靠；`AUDITOR` 可查日志但无业务写权限；不阻塞主流程。
