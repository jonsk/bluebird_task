# 工作日志模块「做减法」评估

> **状态：已执行（2026-10-26）**。本文保留评估时的结构与代价测算；实际落地口径见文末「执行结果」。
> 决策落点：D1 归档 **连能力一起删**；D2 `visibility` **只保留 PRIVATE（仅自己 + 被授权者）**；D3 「全部日志」**保留为 ADMIN 功能并移到后台 `/admin/notes`**；更名**只改中文文案**。

> 评估对象：`frontend/src`（Vue 3 + TS）、`backend/src`（Spring Boot 3）、`scripts/acceptance`、`docs`。
> 目标五件事：① 去除「探索」② 去除「本部门日志」③ 去除「全部日志」④ 去除「归档日志」⑤「下属日志」更名为「员工日志」。
> 评估基线：main 分支 `9600da8`（前端 19 文件 / 121 单测、e2e 63、后端 42 tests、矩阵 117 + 4 全绿）。

---

## 0. 结论先行

1. 五件事分两类，**代价差一个数量级**：
   - **入口减法**（删页面/导航/路由/日历选项，后端 scope 与端点保留）≈ **0.5～1 人日**，风险低、可回滚。
   - **能力减法**（连 `scope` 枚举、`visibility` 枚举、`/archive` 端点、`archived` 语义一起删）≈ **2.5～3.5 人日**，且必须先定 3 个产品语义 + 做数据迁移（真实库现有 **50 条归档日志 / 58 条 INTERNAL / 18 条 PUBLIC**）。
2. 「下属日志」→「员工日志」是**纯文案改名**（前端 5 个文件 + 3 份文档 + 测试断言），≈ **0.2 人日**，无后端改动（配置键与错误码不动）。
3. 建议分批：**P1 入口减法 + 更名先落地**（当天可用），**P2 能力收敛单独一批**（见 §4 决策点，需你拍三件事）。
4. 主要隐性代价不是删代码，而是**测试与视觉基线**：e2e 63 → 约 53～55、单测 121 → 约 100～105、矩阵 117 + 4 → 约 105 + 3、note 相关 8 张 1440/1280 视觉基线全部重制。

### 1.2 后端能力

| 层 | 事实 |
| --- | --- |
| scope 白名单 | `NoteVisibilitySqlBuilder.SCOPES = {mine, shared, explore, internal, subordinate, visible, all}`（7 个） |
| scope → SQL | `scopePredicate()` 7 分支；`explore` = `visibility='PUBLIC'`，`internal` = `INTERNAL AND dept_id IN visibleDeptIds(me)`，`all` = 仅 ADMIN `1=1` |
| 归档 | `archived` 列 + `POST /notes/{id}/archive`、`POST /notes/{id}/unarchive`；`applyArchived()` 仅 `mine`（与 ADMIN 的 `all`）生效，其余 scope 强制 `archived=0` |
| 归档的权限副作用 | `NoteAuthService.isVisible()` 对非 owner 的归档日志直接 `false` → 404；`assertWritable()` 对 EDITOR 抛 `50013`；`fieldPermissions()` 归档后 EDITOR 全 false |
| 可见性枚举 | `PRIVATE / INTERNAL / PUBLIC`，`isVisible` 依次判定 owner → 归档 → 授权 → INTERNAL(部门树) → PUBLIC → 下属开关 |
| 日历 / facet | `/notes/calendar?scope=`、`/notes/tags?scope=` 复用同一 `scopePredicate`，`all` 非 ADMIN 403 |
| SPA 放行 | `SpaRoutes.PAGE_PATTERNS` 用 `/notes/**` 通配（删路由**不影响**放行）；`SAMPLE_PAGES` 里显式列了 `/notes/explore`、`/notes/archived/all`（当前无测试引用，但属文档化样例，需同步） |

### 1.3 真实数据（`backend/data/bluebird.db`，只读统计）

| 指标 | 数量 |
| --- | --- |
| note 总数 / 已逻辑删除 | 481 / 13（存活 468） |
| `archived=1` | **50** |
| `visibility=PRIVATE / INTERNAL / PUBLIC` | **392 / 58 / 18** |

### 2.4 去除「归档日志」

这是**唯一有数据语义**的一项，必须区分两档：

| 方案 | 内容 | 代价 | 数据 |

## 4. 必须先拍的三件事（决策点）

| # | 决策 | 选项 | 推荐 |
| --- | --- | --- | --- |
| D1 | 归档做到哪一档 | A 只删入口（能力/数据保留）／B 连能力删（50 条数据迁移） | **B**。理由：只删入口会让 50 条日志永久不可达，且 `archived` 成为死字段；若你希望保留历史可改「回收站」放设置页（第三种：入口移到 `/admin`，成本与 B 相近） |
| D2 | `visibility` 是否一起收敛 | ① 只删页面、枚举保留（PRIVATE/INTERNAL/PUBLIC 仍可写）／② 收敛为 PRIVATE + INTERNAL（删 PUBLIC，18 条迁移）／③ 只留 PRIVATE（58+18 条迁移，语义最简） | **①（P1 阶段）→ ②（P2 阶段）**。① 的风险是「公开日志无处可看」，但改动最小；② 需明确「公开」是否还有业务价值 |
| D3 | 删除「全部日志」后 ADMIN 怎么全库检索 | ① 接受失去（改用后台/数据库）／② 保留 API 但无 UI（`scope=all` 仅在管理后台复用）／③ 迁到 `/admin/logs` 页面 | **②**。保留矩阵 #8/#8a 的契约意义，避免 ADMIN 审计能力真的消失 |

> 其余小决策：① `员工日志` 是只改中文文案，还是连路由 `/notes/subordinate`、`note-subordinate` data-test 一起改成 `employee`（推荐只改文案）；② 更名是否同步到后端 `app.security.manager-can-read-subordinate` 配置键（推荐不改）。
