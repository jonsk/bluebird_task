# 减法评估：授权日志（note_user_grant）

> 评估日期：2026-10-26
> 评估对象：工作日志「授权管理 / 被授权日志」整套能力（`note_user_grant` 表 + `/api/v1/note-grants` 6 个端点 + `scope=shared` + `VIEWER/EDITOR` 角色 + `NoteUserGrantView` / `NoteGrantForm`）
> 前置：本轮已完成「去归档 / 去 visibility / 去 explore+internal / scope 7→5 / 全部日志移后台」，本评估基于**减法后**的代码基线。
> 结论：**技术可删，代价可控（约 3.5 人日），但会把「同事/上下级/审计」三类跨人可见性彻底归零**，必须先回答第 7 节的三个决策问题；若只是嫌页面复杂，还有成本更低的中间档。

---

## 0. 一句话结论

| 维度 | 判断 |
|---|---|
| 技术可行性 | ✅ 无外部模块依赖，`note` 模块内自治，可整块摘除 |
| 影响半径 | 中：后端 ~460 行 / 前端 ~750 行 / 6 个端点 / 1 张表 / 8 个错误码 / 19 条矩阵用例 |
| 数据不可逆性 | ⚠️ 真实库 31 条授权记录（5 条 APPROVED），删除后无法恢复「谁曾把日志开放给谁」 |
| 业务副作用 | ⚠️ **审计员将看不到任何日志**（当前 446 条全部依赖张丽的 APPROVED 授权）；李四的 EDITOR 协作编辑消失 |
| 推荐 | 若确定不做「跨人共享日志」，走 **L2 全量摘除 + 表保留归档**；否则走 **L1 只摘入口**，先观察 2 周 |

## 2. 减法深度：三个选项

| 选项 | 内容 | 成本 | 残留 | 适用 |
|---|---|---|---|---|
| **L1 只摘入口** | 前端删 `NoteUserGrantView`/`NoteSharedView` + 导航项，后端与 `scope=shared` 原样保留 | 0.5 人日 | 死端点仍在（openapi/契约不红）、`被授权` 数据仍生效但**用户无法自查**；矩阵 D 组继续 PASS | 只是不想让用户看到这个页面，先观察 |
| **L2 全量摘除（推荐，若确定不做共享）** | L1 + 删 6 端点/服务/状态机/`scope=shared`/EDITOR/8 个错误码 + 单测/e2e/矩阵/文档同步 + V8 迁移 | 3.5 人日 | `note_user_grant` 表**保留**（加注释 deprecated，不做 DROP），历史可追溯 | 日志为纯个人记录，跨人只保留「上级看下属」 |
| **L3 全量摘除 + 清表** | L2 + `DROP TABLE note_user_grant` | 3.6 人日 | 无 | 确定永不复用，且不介意审计断链 |

> 另有一条**反向**路线（成本 1.5 人日）：保留但降级为「一档只读分享」——去掉 SUPERIOR 待确认流程、去掉 EDITOR 升级、去掉 ADMIN 代授权，只留「我把日志只读开放给某人 / 随时收回」。这不是减法而是重做，仅在"需要共享但嫌复杂"时选。

## 3. 影响面逐项

### 3.1 后端行为变化

| 场景 | 现状 | 删后 |
|---|---|---|
| 他人日志详情/列表 | 有 APPROVED 授权即可见 | **404**（不暴露存在性） |
| `GET /notes?scope=shared` | 被授权人日志列表 | **400 + 10001**（非法 scope，与 explore/internal 同款处理） |
| 协作编辑 | EDITOR 可改正文 + 日志日期，不可改标签/附件/置顶 | 全部 403（只剩 owner / ADMIN） |
| `NoteVO.grantRole` / `fieldPermissions` | `OWNER/ADMIN/VIEWER/EDITOR/null` + 三字段布尔 | 只剩 `OWNER/ADMIN/null`；`fieldPermissions` 恒 `all` 或 `none` |
| 字段级权限错误 50013 | EDITOR 改标签触发 | 不可达 |
| 审计埋点 | `grant-create/approve/reject/upgrade/revoke` 5 个 action | 不再产生，历史行保留 |

### 3.2 谁能看到什么（真实库量化，`manager-can-read-subordinate=true`）

| 用户 | 现在可见日志 | 删授权后可见 | 变化 |
|---|---|---|---|
| 张丽（技术部负责人） | 自己的 446 + 李四 23 + 王五 4 | 自己的 446 + 下属 27（走员工日志） | 基本无损 ✅ |
| 李四（前端组） | 自己的 23 + 张丽 446（EDITOR） | 自己的 23 | **-446，且失去编辑权** ⚠️ |
| 王五（后端组） | 自己的 4 + 李四 23 | 自己的 4 | -23 |
| 审计员（AUDITOR） | 张丽 446（VIEWER） | **0** | **-446，角色空转** 🚨 |
| 人事管理员（USER_MANAGER） | 自己的 | 自己的 | 无（其授权均已 REVOKED） |
| admin / 验收管理员 | 全部（ADMIN） | 全部 | 无 |

> 结论：**「上级看下属」有 `员工日志` 兜底，`授权` 真正不可替代的只剩两类——「下属/平级看上级」（李四）和「审计员看业务日志」（审计员）。**

### 3.3 契约与门禁

- `docs/api/openapi.yaml`：删 6 个 op、5 个 path；`docs/contract` 接口表删 6 行。
- `check-contract.mjs` 存量红 50 项**不受影响**（不新增红项），但总数基线（README 里写的 117/119/121）需再调一次。
- 若走 L1：openapi 与接口表都不动，契约零影响。

### 3.4 数据与迁移

- V8 迁移只需 `-- deprecated` 注释（L2）或 `DROP TABLE`（L3）；**不需要回填存量 note**，因为 `visibility` 已在 V7 归零。
- 26 条 REVOKED 记录是「授权 → 撤销」的合规证据链，**建议导出 CSV 存档**（`docs/` 不放数据，放 `backend/data/archive/` 或由运维另存）。
- 附件/引用（`note_attachment`、`note_relation`）不受影响：它们跟随 note 可见性，不跟随 grant。

### 3.5 现有功能不受影响的部分

员工日志（subordinate）、全部日志（`/admin/notes`）、日历、标签 facet、置顶、删除、附件、引用、版本冲突、mock、任务模块 —— 均无 grant 依赖，**零改动**。

## 6. 与「本轮减法」的一致性

本轮已删掉 3 个视图（探索/本部门/归档）并把可见性简化为"自己 + 上级 + 管理员 + 被授权"。再删授权，模型即为：

```
可见 = 自己 ∨ (上级 ∧ 开关开启) ∨ ADMIN
可改 = 自己 ∨ ADMIN
```

这是**最简也是最好解释**的一套规则，与"工作日志是个人记录"的产品定位一致；代价是彻底放弃「日志作为协作/审计载体」的用法。

## 7. 需要拍板的三个问题

1. **审计员怎么办？** 删授权后 AUDITOR 无日志入口。是 (a) 给 `/admin/notes` 加 AUDITOR 只读（+0.1 人日），还是 (b) 接受审计员不看日志，还是 (c) 因此保留授权？
2. **「下属/平级看上级」是否必需？** 李四对张丽 446 条日志的 EDITOR 是真实在用场景（且员工日志无法覆盖"向上看"）。若无此需求 → 直接 L2。
3. **表怎么处理？** 保留 deprecated（可追溯，推荐）还是 DROP（干净但断链）？

> 三个问题答完即可开工；若答案倾向"保留能力"，则改为 L1（只摘页面入口），0.5 人日，且不动契约与数据。
